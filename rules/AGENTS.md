# Coding & Workflow Style

> **CRITICAL — 이 규칙들은 협상 불가다. 요청 크기·긴박도와 무관하게 예외는 없다.**

## Part 1. Coding Style

> | MUST | NEVER |
> |------|-------|
> | 요청된 범위만 수정 | 요청 범위를 초과한 수정 금지 |
> | 새 식별자는 즉시 이해 가능한 풀어쓴 이름 | `data`, `value`, `flag`, `temp`, `info`, `result` 등 범용 이름 금지 |
> | 새 코드·주석에 약어 사용 금지 | `fb`, `cfg`, `mgr`, `tmp` 등 의미 불명확한 약어 금지 |
> | 같은 속성은 단일 출처(SSOT)에서만 관리 | 같은 값을 여러 곳에 복사·중복 저장 금지 |

**이런 생각이 들면 멈춰라 — 합리화다:**

| 이 생각 | 사실 |
|--------|------|
| "주변 코드도 같이 정리해주면 좋겠다" | 요청된 것만 수정한다. 인접 코드 개선은 금지다. |
| "나중에 쓸 수 있으니 유연하게 만들어두자" | 투기적 추상화는 금지다. 지금 필요한 것만 만든다. |
| "이 값은 두 곳에 있어도 관리가 쉽겠다" | 복사본은 결국 어긋난다. 단일 출처만 허용한다. |

### A. 작업 전 사고방식

코드를 쓰기 전에:

- **불확실하면 멈추고 묻는다.** 가정을 숨기지 않고 명시하고, 헷갈리면 무엇이 불명확한지 짚는다.
- **해석이 여러 갈래면 펼쳐 보인다.** 조용히 하나를 고르지 않는다.
- **더 단순한 길이 있으면 말한다.** 정당하면 푸시백한다.
- **수정 범위가 크면 먼저 제안한다.** 조용히 어느 방향을 택하지 않는다.
  - 외과적 변경으로 우선 처리할 수 있는지 검토한다.
  - 구조 리팩토링이 필요하다면 이유(예: 중복 누적, 의존성 역전, 확장 불가 구조 등)를 명시한 뒤 두 선택지를 사용자에게 제안한다.

판단 기준: "시니어 엔지니어가 이거 과하다고 할까?" → 그렇다면 단순화.

성공 기준을 **검증 가능한 목표**로 바꾼 뒤 그 기준이 충족될 때까지 루프한다.

- "검증 추가" → "잘못된 입력 테스트를 쓰고 통과시킨다"
- "버그 수정" → "버그를 재현하는 테스트를 쓰고 통과시킨다"
- "X 리팩토링" → "전후로 테스트가 통과하는지 보장한다"

### B. 코딩 패턴 / 코드 품질 규칙

#### 1. 단순함 우선
- **요청된 것만.** 투기적 기능·추상화·유연성·불가능 시나리오 방어는 요청이 없으면 추가하지 않는다.
- 외과적 변경이 기본이나, 전면 재작성이 명확히 더 단순하다면 재작성한다.
- **기존 구현 요소를 먼저 살핀다.** 유사한 패턴·유틸·컴포넌트가 이미 있으면 새로 만들지 않고 재활용한다.
- **전체 아키텍처에 미치는 영향을 먼저 파악한다.** 부분 변경이 전체 구조의 일관성을 깨지 않는지 확인한다.
- 기존 코드 편집 시: 인접 코드/주석/포맷을 "개선"하지 않는다. **요청 범위 밖을 건드리면 리뷰에서 거절된다.**
- 내 변경이 만든 orphan(미사용 import/변수/함수)만 정리. 기존 dead code는 건드리지 않고 **언급만** 한다.
- 테스트: 바뀐 모든 줄이 요청에 직접 추적돼야 한다.

#### 2. 불필요한 마이그레이션 코드 금지
- 데이터 파일을 직접 교체할 수 있으면 직접 바꾼다.
- 로더에 normalize/lazy-migration 분기를 끼워넣지 않는다 (한 번 쓰이고 영원히 남는 레거시가 됨).

#### 3. 단일 출처(SSOT)
- **같은 속성의 사본을 여러 곳에 저장하지 않는다. 복사본은 반드시 어긋난다.**
- 한 곳에서 조회하는 getter를 두고 하위는 그 출처를 신뢰한다.
- 규칙·설정도 단일 출처에 codify하고, 다른 문서는 *왜/사례* 보존용으로만 둔다.

#### 4. 헬퍼는 객체 단일 인자, 사소한 래퍼 금지
- `a || b || fallback` 같은 사소한 표현식을 named 함수로 감싸지 않는다 (단일 사용 추상화 금지).
- 헬퍼가 정당하면(여러 호출처가 같은 객체를 다룸) 위치 인자 대신 **도메인 객체 하나**를 받아 내부에서 추출한다.
  - 예: `pickReplyText(result)` (O) vs `pickReplyText(a, b, c)` (X).

#### 5. 약어·줄임말 금지, 즉시 이해 가능한 이름
- **새 식별자(변수·함수)와 주석에 의미 불명확한 약어는 절대 쓰지 않는다.** 풀어쓴 이름을 쓴다 (`fb` → `fileBrowser`).
- 기존 약어를 일괄 개명할 필요는 없으나, 새로 쓰는 코드·주석은 약어 없이.
- **이름만 읽고도 무엇을 담는지 즉시 알 수 있어야 한다.** 모호하면 틀린 이름이다.
  - 좋은 예: `userProfileImageUrl`, `retryDelayMilliseconds`, `isSubmitButtonDisabled`
  - 나쁜 예: `data`, `value`, `flag`, `temp`, `info`, `result`
- 타입·컨텍스트로 이미 명확한 부분은 반복하지 않되, 불명확하면 길어져도 풀어 쓴다.

#### 6. 레거시 식별자 잔재 금지
- 기능 개편 시 옛 설계의 슬롯 번호·모드명이 이름에 남으면(예: `custom1`) 새 설계 기준으로 함께 개명한다.
- 사용자 저장값(localStorage 키 등)이 걸려 있어도 중요도 낮으면 마이그레이션 없이 키를 바꾼다.
- **키 변경으로 기존 코드가 깨진다면** 마이그레이션 스크립트 또는 서지컬 호환 코드를 추가한다.
  - 해당 코드에는 반드시 `COMPAT` 태그를 달고, 아래 정보를 모두 포함한다:
    1. 어떤 커밋(커밋 SHA 또는 PR)에서 구 식별자가 도입됐는지
    2. 마이그레이션을 추가하는 시점의 버전(앱 버전, 스키마 버전 등)과 작업 내용
    3. 언제 이 코드를 제거해도 되는지(`COMPAT-REMOVE-WHEN`)
  - 예:
    ```
    // COMPAT(custom1-slot-rename): custom1 -> primarySlot 개명 (commit abc1234, v2.3.0)
    //   구버전 저장값을 읽어 새 키로 이전 후 구 키를 삭제한다
    // COMPAT-REMOVE-WHEN: v2.3.0 이전 버전 사용률 0% 확인 후 30일 경과 시
    ```

#### 7. 확장 포인트엔 관리 주석
- 화이트리스트·레지스트리 등 확장 목록의 정의부 주석에 (1) 추가 절차, (2) 플래그/데이터 흐름, (3) 엣지 케이스를 남긴다.

#### 8. 부수 기능에 강한 의존성 금지
- 표시·부가 기능 때문에 런타임 의존성(예: 컨테이너 `.git` 마운트, 런타임 git 호출)을 추가하지 않는다.
- 호스트 스크립트·CI 스텝·기존 데이터 경로 재활용을 우선한다.
- "고작 이 효용에 비해 무거운 수단 아닌가"를 자문한다.

#### 9. 중요도 대비 복잡도로 기각 가능
- 코드 리뷰에서 발견된 사항이 추가하는 복잡도가 기능 중요도보다 크면 **한 줄 사유와 함께 기각**한다.
- 오타급·한두 줄 수정은 그대로 적용한다.

### C. 코드 주석 태그 시스템

"나중에 처리해야 할 코드"를 추적하는 태그 시스템. 흩어진 대상을 grep 한 줄로 인덱싱한다.

**공통 포맷** — 이유 줄 + 제거 조건 줄:
```
// <TAG>(<subject>): <이 코드가 존재하는 이유>
// <TAG>-REMOVE-WHEN: <이 조건이 충족되면 코드와 태그를 함께 제거>
```

전체 목록: `grep -rn "FIXME\|REFAC\|COMPAT\|QUIRK" src/`

---

**FIXME** — 알려진 버그·문제. `<subject>`에 지금 고치지 못하는 이유를 적는다.
```
// FIXME(time-constraint): 입력 범위 미검증 — 서버에서 걸러지나 클라 피드백 없음
// FIXME-REMOVE-WHEN: 클라이언트 validation 추가 시
```

**REFAC** — 기술 부채·리팩토링 대상. 왜 지금이 아닌지 이유를 포함한다.
```
// REFAC(scope-too-large): 이 함수 200줄, 3개 책임 혼재
// REFAC-REMOVE-WHEN: 해당 모듈 분리 작업 착수 시
```

**COMPAT** — 하위 호환을 위해 존재하는 코드. 구버전 클라이언트·API·스키마·설정 포맷을
지원하기 위한 분기·변환·fallback에 단다. `<subject>`에 무엇을 지원하는지 명시하고,
REMOVE-WHEN에 "언제 그 지원이 불필요해지는가"를 구체적으로 적는다.
일반 기능 코드에 달지 않는다 — "이 코드가 없으면 구버전이 깨진다"는 경우에만.
```
// COMPAT(v1-session-format): 구버전 .claude 디렉토리 구조를 신규 경로로 마이그레이션
// COMPAT-REMOVE-WHEN: v1 세션 파일을 생성하는 클라이언트 버전의 사용률이 0%가 되고
//   최소 30일 이상 경과한 뒤, 마이그레이션 로그에서 실행 흔적이 없음을 확인했을 때
```

**QUIRK** — 외부 컴포넌트(라이브러리·엔진·모델 등)의 비표준 동작을 보정·우회하는 코드.
해당 컴포넌트가 표준대로 동작했다면 없었을 코드에만 단다.
`<subject>`에 무엇이 잘못 동작하는지 적는다. 근본 원인이 우리 쪽(설정·호출 방식)이라면
출처를 함께 고치고 QUIRK를 달지 않는다.
```
// QUIRK(some-lib@2.x): 응답 Content-Type 헤더 누락 — 수동으로 주입
// QUIRK-REMOVE-WHEN: some-lib 3.0 업그레이드 후 (패치노트 #1234 확인)
```

## Part 2. Workflow Style

> | MUST | NEVER |
> |------|-------|
> | 첫 편집 전 `git rev-parse`로 git 여부 **직접** 검증 | 환경 헤더 `Is a git repository` 값 신뢰 금지 |
> | git 레포이면 **반드시** worktree 생성 후 편집 | main tree에서 파일 직접 편집 금지 |
> | 사소하지 않은 변경이면 빌드·테스트 전 diff 검토 실행 | 사소하지 않은 변경을 diff 검토 없이 진행 금지 |
> | 머지 전 diff 검토 → 사용자 승인 순서 준수 | 승인 없이 머지 금지 (머지 = merge+push) |

**이런 생각이 들면 멈춰라 — 합리화다:**

| 이 생각 | 사실 |
|--------|------|
| "한 줄 수정이라 worktree 없이 해도 되겠다" | 크기와 무관하다. worktree는 격리를 위한 것이다. |
| "환경 헤더가 git 아니라고 하니까 그냥 편집해도 되겠다" | 헤더는 실제로 틀린 사례가 있다. 반드시 직접 검증한다. |
| "이건 간단한 수정이라 diff 검토 생략해도 되겠다" | 오타·1-2줄 이하 수정만 생략 가능하다. 확신이 없으면 실행한다. |
| "diff 검토는 나중에 해도 되겠다" | 빌드·테스트 전과 머지 전, 두 시점 모두 고정이다. |
| "사용자가 빨리 하라고 했으니 승인 생략해도 되겠다" | 빠른 실행과 승인 생략은 별개다. |

### A. git 작업: worktree 기반 (핵심)

git이 있는 모든 환경에서 **편집은 worktree에서** 한다. main tree는 읽기·조사·머지 전용.
이유: 편집 중 dirty 상태가 다른 작업/머지를 막고, 작업이 격리돼야 깨끗한 브랜치 경계가 남는다.

절차:

0. **첫 편집 전, git 여부를 직접 검증한다 — 환경 헤더를 신뢰하지 않는다.**
   - 세션 환경 메타데이터의 `Is a git repository` 값은 **틀릴 수 있다**(실제 오보 사례 있음).
     이 검증이 그 헤더 값을 **오버라이드**한다.
   - 작업 디렉토리에서 `git rev-parse --is-inside-work-tree 2>/dev/null`을 실행한다.
   - `true`가 출력되면 — 헤더가 `false`라고 했더라도 — 무조건 아래 worktree 절차를 탄다.
   - 그 외(오류 포함)이면 git 레포가 아님으로 판단하고 worktree 절차는 생략한다.

1. **첫 편집 전에 worktree부터.** 반드시 `git fetch origin`으로 base를 최신화한 뒤 만든다.
   - `git fetch origin && git worktree add --no-track -b work/<주제> ../<레포명>-wt-<주제> origin/<기본브랜치>`
   - 경로는 **레포 한 단계 위**에 `../<레포명>-wt-<주제>` 형식으로 만든다. (예: `../fdc-bot-wt-auth-fix`)
   - **기본 브랜치명은 레포마다 다르다.** `master` 또는 `main` 중 하나이므로 작업 전 `git remote show origin | grep 'HEAD branch'`로 확인한다.
2. **`--no-track` 필수.** upstream이 `origin/master`로 잡히면 GUI의 pull/sync가 작업 커밋을 기본 브랜치로 직행 push할 수 있다(실제 사고 사례).
3. **모든 Read/Edit는 worktree 경로에서.** 커밋은 `git add <개별 파일>`로 **내 파일만** — `git add -A`·`git add src/` 금지(다른 미커밋 작업이 휩쓸려 들어감).
4. **rebase까지만 worktree에서.** 머지 단계(`checkout <기본브랜치>`·`merge`·`push`·`worktree remove`)는 **main tree에서** 실행한다.
   - worktree 안에서 기본 브랜치를 checkout하면 `'master(main)' is already used by worktree`로 실패하고, 체인이 끊기면 작업 브랜치가 원격에 잘못 push된다.
5. **작업 디렉토리가 shallow면** 머지가 unrelated histories로 막힐 수 있다. `git fetch --unshallow origin`으로 복구.
6. **원격(`origin`)이 없는 로컬 단독 레포**는 fetch/push/`origin/<base>` 단계를 전부 생략한다.
   - `git remote`가 비어 있으면 이 케이스에 해당한다.
   - worktree base를 원격 대신 **로컬 기본 브랜치**로 잡는다:
     `git worktree add --no-track -b work/<주제> ../<레포명>-wt-<주제> <기본브랜치>`
   - 머지는 로컬에서 `--no-ff`만 하고 push는 없다.
   - "편집은 worktree, main은 머지 전용" 원칙은 원격 유무와 무관하게 동일하게 지킨다.
7. **서브 worktree(중첩) 패턴.** 작업용 상위 worktree가 이미 특정 브랜치(예: `stage`)를 checkout 중일 때,
   그 위에 하위 worktree로 작업 브랜치를 얹는 구조.
   - 구조 예:
     ```
     my-repo            (master 브랜치)
     my-repo-wt-stage   (stage 브랜치 checkout — 상시 작업 상위 worktree)
     my-repo-wt-stage-task1 (stage 기반 작업 브랜치 — 실제 편집 장소)
     ```
   - 하위 worktree 생성: base는 상위 브랜치(`stage`)다.
     `git worktree add --no-track -b work/<주제> ../<레포명>-wt-<상위>-<주제> <상위브랜치>`
     (예: `git worktree add --no-track -b work/task1 ../my-repo-wt-stage-task1 stage`)
   - Read/Edit·rebase·커밋은 하위 worktree에서 기존 규칙(개별 파일 add, `--no-track`)을 그대로 따른다.
   - 머지 대상이 **상위 브랜치(`stage`)** 일 때: git은 한 브랜치를 한 worktree에서만 checkout하므로,
     main tree에서 `stage`를 checkout하려다 `'stage' is already used by worktree`로 막힌다.
     따라서 **`stage`를 checkout 중인 상위 worktree(`my-repo-wt-stage`)에서 `--no-ff` 머지**한다.
   - 상위 worktree의 브랜치로 머지 후, 그 결과를 기본 브랜치(main/master)로 올리는 것은 별도 관리한다.

### B. 커밋 · 머지 · push

- **작업 완료 후 자동 커밋 + push.** 논리적 단위가 끝나면 묻지 않고 커밋하고 push까지 한다.
- **연속 리팩토링은 push를 마지막에 한 번.** 여러 독립 커밋이 쌓이는 작업은 중간 push 생략, 마지막에 한 번. (CI 중복 빌드 방지)
  - 독립 단일 작업은 완료 즉시 push.
- **커밋 메시지에 작성자 정보(`Co-Authored-By`) 미포함.** 기본값을 두지 말고 작업 내용을 한 줄로 적는다.
- **기본 브랜치에 직접 커밋하지 않는다.** 작업은 작업 브랜치(`work/<주제>`)에서.
- **작업 중 중간 rebase.** 작업이 길어지면 주기적으로 `git fetch origin`으로 기본 브랜치 업데이트를 확인한다.
  - 새 커밋이 쌓였으면 `git rebase origin/<기본브랜치>`로 미리 올려 충돌을 조기에 해소한다.
  - 충돌이 크면 사용자에게 알리고 함께 해결한다.
- **머지 전 순서: rebase → diff 검토 → code-review → commit → 빌드·테스트 → 사용자 승인 → merge. 이 순서를 생략하거나 바꾸는 것은 허용되지 않는다.**
  1. worktree에서 `git fetch origin && git rebase origin/<기본브랜치>` — 최신 기본 브랜치 위로 올린다. (충돌 시에만 멈추고 알린다.)
  2. **diff를 reuse·simplification·efficiency·altitude 4개 관점으로 검토해 수정한다.** 오타·1-2줄 이하의 사소한 수정이면 생략할 수 있다.
  3. **`code-review` 스킬(또는 `/code-review`)을 호출한다.** 발견된 문제가 있으면 수정한다.
  4. 변경사항을 커밋한다 — worktree 내 커밋이므로 승인 없이 진행한다.
  5. 빌드·테스트를 실행해 diff 검토·code-review 이후에도 동작이 정상임을 확인한다.
  6. 변경 요약(무엇을 바꿨는지)을 사용자에게 보여주고 머지 승인을 **명시적으로** 받는다. 사용자가 응답하기 전까지 머지하지 않는다.
  7. 승인 후 main tree에서 `--no-ff` merge → push 진행.
  8. push까지 성공적으로 완료된 것을 확인한 뒤 worktree를 삭제한다. merge가 완전히 끝나기 전에는 삭제하지 않는다 — 언제든 재시도할 수 있도록 보관한다.
- **준선형(semi-linear) 머지.** `fetch → rebase origin/<기본브랜치>`로 ff 가능 상태를 만든 뒤, 일부러 `--no-ff` 머지로 작업 경계를 남긴다.
  - push가 거부되면(race) 그래프를 재구성한 뒤 push한다. 단순 재시도가 아니라 다음 순서를 완수해야 한다:
    1. main tree를 `git reset --hard origin/<기본브랜치>`로 원복한다.
    2. worktree에서 `git fetch origin && git rebase origin/<기본브랜치>`로 작업 브랜치를 새 tip 위로 올린다. (충돌 시 멈추고 알린다.)
    3. main tree로 돌아와 `git merge --no-ff work/<주제>` → `git push`한다.
    4. 이 사이클을 push가 성공할 때까지 반복한다.
- **커밋 전 사용자 가이드 영향 확인.** 기능·동작·구조가 바뀌면 README 등 사용자 가이드도 **같은 커밋**에 갱신한다.
  - API 변경 시 API 문서도 함께 업데이트.
- **prod 서비스 교체는 에이전트가 직접 실행하지 않는다.** 코드 변경·커밋·push까지 담당하고, 실제 서비스 교체(배포)는 사용자에게 제안에 그친다.

### C. 에이전트 응답 스타일

- **자율(오토) 모드 전 예상 소요 시간 제시.** 자율 실행 직전 ETA를 먼저 보여준다.
- **git 단계 완료 시 ASCII 박스 시그니처.** worktree 생성·rebase·diff 검토·commit·빌드 통과·머지·dev 배포 완료 시 아래 형식의 박스를 출력한다.
  - 내용은 **ASCII만** — 한글·이모지·`→`(더블폭) 금지. 화살표는 `->`. 모든 줄을 같은 폭으로 패딩.
  - **prod 배포는 사용자가 직접** 실행하므로 박스 대상이 아니다. git 단계(worktree·머지·dev 배포)만.
  - 라벨은 **대문자**로 시작하고 콜론(`:`)으로 정렬한다.
  - **세로선 없이 위아래 가로선만** 사용한다. 가로선은 `═` 60자로 고정.

  머지 완료:
  ```
  ════════════════════════════════════════════════════════════
    Merged to <base-branch> · Pushed
  ────────────────────────────────────────────────────────────
    Repo    : <owner>/<repo>
    Merged  : work/<topic> -> <base-branch>
    Commit  : <sha7>  "<commit message>"
    Changed : <N> files  +<ins> -<del>
  ════════════════════════════════════════════════════════════
  ```

  cleanup 완료 (머지 박스 직후 출력):
  ```
  ════════════════════════════════════════════════════════════
    Cleanup done
  ────────────────────────────────────────────────────────────
    Repo    : <owner>/<repo>
    Worktree: ../<repo>-wt-<topic> removed
    Branch  : work/<topic> deleted (local + remote)
  ════════════════════════════════════════════════════════════
  ```

  worktree 생성:
  ```
  ════════════════════════════════════════════════════════════
    Worktree created
  ────────────────────────────────────────────────────────────
    Repo    : <owner>/<repo>
    Worktree: ../<repo>-wt-<topic>
    Branch  : work/<topic>
    Base    : origin/<base-branch> @ <sha7>
  ════════════════════════════════════════════════════════════
  ```

  rebase 완료:
  ```
  ════════════════════════════════════════════════════════════
    Rebased
  ────────────────────────────────────────────────────────────
    Repo    : <owner>/<repo>
    Branch  : work/<topic>
    Base    : origin/<base-branch> @ <sha7>
  ════════════════════════════════════════════════════════════
  ```

  diff 검토 완료:
  ```
  ════════════════════════════════════════════════════════════
    Diff review done
  ────────────────────────────────────────────────────────────
    Repo    : <owner>/<repo>
    Branch  : work/<topic>
    Changed : <N> files  +<ins> -<del>
  ════════════════════════════════════════════════════════════
  ```

  commit 완료:
  ```
  ════════════════════════════════════════════════════════════
    Committed
  ────────────────────────────────────────────────────────────
    Repo    : <owner>/<repo>
    Branch  : work/<topic>
    Commit  : <sha7>  "<commit message>"
    Changed : <N> files  +<ins> -<del>
  ════════════════════════════════════════════════════════════
  ```

  빌드·테스트 통과:
  ```
  ════════════════════════════════════════════════════════════
    Build passed
  ────────────────────────────────────────────────────────────
    Repo    : <owner>/<repo>
    Branch  : work/<topic>
  ════════════════════════════════════════════════════════════
  ```

  push race 재시도 후 완료:
  ```
  ════════════════════════════════════════════════════════════
    Push retried · Pushed
  ────────────────────────────────────────────────────────────
    Repo    : <owner>/<repo>
    Merged  : work/<topic> -> <base-branch>
    Commit  : <sha7>  "<commit message>"
    Retries : <N>
  ════════════════════════════════════════════════════════════
  ```

- **한국어로 응답한다.** 기술 용어·코드 식별자는 원형 유지.
- **불확실한 사실은 메모리/추측이 아니라 코드·문서로 검증**한 뒤 말한다.
- **설계 결정의 이유를 먼저 설명한다.** 파일명·디렉토리명·구조 등 의도가 있는 선택은 "왜 그렇게 했는지"를 사용자가 묻기 전에 명확히 밝힌다. "이유 없다"고 단정하기 전에 다시 생각한다.
- **글·문서는 줄을 짧게.** 한 불릿·문장에 몰아넣지 말고 짧게 끊어 별도 줄로 분리한다.
  - 성격이 다른 내용(동기 vs 동작)은 줄을 나눈다.
